# Prepare the service packet

Produce supported editable drafts automatically. The agent interprets sources and maintains JSON; the user does not fill out a schema. Never print, distribute, finalize, or alter schedules during preparation.

## Read before running

From the project root, read `docs/service-packets/operations.md`, `desktop-jobs.md` in that directory, and `state/service_packets/runtime.json`. Read the public functions in `service_packets/{collection,sources,model,build}.py`. The runtime file identifies interpreter, folders, Google Doc and templates; operations explains candidate-to-snapshot mapping. If unavailable, report the dependency; do not invent another worker or schema.

## Build and handoff

Construct the validated packet using actual service times, original text/evidence, accepted corrections, scoped sources, and explicit `heading_paragraphs`/`bulletin_paragraphs`. Use maintained layout/cue configuration and actual technical templates. Preserve OOW Heading, standing closing text and approved body styles. Apply approved routine cues; flag changed performers and unknown assignments. For every main-service item, supply `technical_wording` containing only the worship-order designation and title (or reading reference). Do not put participants, composers, arrangers, credits, or slide instructions in the Camera/Sound worship-element cell. Keep detailed source/bulletin wording separately, and operational assignments or uncertainty in their cue columns.

Collect and interpret all service sources, but call `build_packet(..., phase="main")` first (the default). This generates the main bulletin, Camera, Sound and Proclaim using the previous Sunday's finalized main baseline; early bulletins are deferred, not treated as cancelled. The user updates common calendar, announcements and personnel in the main bulletin and explicitly designates its saved final. After capture, call `build_packet(..., phase="early")` with `packet["baseline"]` set to the returned captured baseline for the same Sunday, not the previous phase's frozen pointer. Each early bulletin starts independently from that same finalized main baseline; no main/technical files are regenerated in this phase. No date exception bypasses the same-week requirement. Combined services have no early stage. Never infer finalization from time or file presence. Missing orders remain findings; missing baseline permits main technical/Proclaim drafts. Never synchronize or overwrite later manual edits. Inherited common copy is reviewed in the main stage; early drafts preserve it byte-for-byte outside the two replaced stories.

For each main-service item, author a nonempty `proclaim` list of blocks: `{ "label": "Lyrics", "text": "full supplied text", "evidence": [{"source_id": "music", "location": "body / anthem text"}] }`. Include all supplied verses, participants, credits, publishing details, lyrics, spoken text and applicable slide directions at their ordered item. Explicitly state unavailable material instead of inventing it. `proclaim_notes` holds sourced review/asset notes. The renderer preserves these blocks and emits visible findings when enrichment is missing. Proclaim is an internal working document: prioritize complete details and easy scanning, not page count or finely controlled pagination. Camera and Sound remain concise.

Queue native proof jobs with `scheduled.queue_job`, then start the registered on-demand task. Do not write `<job-id>-request.json`, `<job-id>.log`, or native request/result files: those belong exclusively to the worker. Any extra audit copy goes in build metadata outside the desktop spool, never between submission and launch at a worker-owned path. Never replace dispatch directly, bypass locks, create another spool, or clear a lock because it is old. Busy apps defer proof; unresolved desktop ownership blocks desktop work, not independent local generation. Inspect every new proof page; identical raster comparisons may cover unchanged pages.

Read actual output XML/DOCX text and verify every accepted correction in all dependent artifacts; the builder does not synchronize values, display wording and bulletin paragraphs automatically. Deliver exact artifact links and separate generation, proof and editorial status. Text fit, overset and panel breaks are human cleanup, not delivery blockers or permission to shrink/delete content. Reused drafts retain pending proof work. Run from `C:/Coding Projects/Document-Generator` on main. Maintain six stable weekly documents in `outputs/YYYY-MM-DD/`, using the builder's returned paths. Corrections replace unedited generated results in place; never create a new revision folder or duplicate the handoff. Preserve user edits and unknown existing files; a `manual_edits_preserved` finding means the new correction was not applied to that file and needs reconciliation. Do not claim it is updated. Use the returned `manifest_path` for proof status and keep current proof assets outside the six-document handoff. Temporary attempts are not deliverables. Leave old revision folders and unrelated untracked files alone. Never promote a draft as next week's baseline.
